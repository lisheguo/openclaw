## 阶段、失败恢复和完成条件

所有步骤均为 Hook 观察和本地 Shadow 判定；插件不调用 GLPI，不自动执行这些动作。

1. 本人 Flow 完成预检、实时列表、窄实体确认、最终预览送达和本人确认后，才可得到创建授权判定。host sender/session/run/call 与参数快照绑定；每个 Flow 同时仅登记一个待完成操作。
2. `CREATE_IN_PROGRESS` 等待相关回执。完整 success=true + 正 ticket ID → `CREATED`，保存创建时的草稿快照与 ID。错误、丢失/不完整回执 → `CREATE_OUTCOME_UNKNOWN`，保留 Flow、不建议重建。没收到 after 回调则一直待核对，不能靠固定超时宣称失败。
3. 目标 2：绑定 ID → 请求 update(2) → 新 get_ticket 证实 2 才完成。创建后的初始状态恰好为 2 也不能替代明确更新步骤。
4. 目标 5：关联 add_solution 成功回执 → 新读回。如果已为 5 且有 solution 计数，完成；如果为 1–4，反馈 `BLOCKED_VERIFY_SERVER_TRANSITION_BEFORE_UPDATE_5`。离线测试另模拟候选 update(5) 后读回，不能据此宣称生产迁移被允许。
5. 目标 6：关联 solution 并实际观察到 5 → 对候选 update(6) 的回执再读回 6，才完成。反馈同样要求先验证服务端迁移规则；直接看到 6 或单独 update 回执不足。
6. add_solution 结果未知时禁止自动重加；读回有计数也不能补出本次 solution ID。update 失败/回执丢失可先读同一 ID：实际达到目标且授权仍有效可完成，否则保留该 ID，在已观察阶段继续候选 update，不能重新 create。重复 call ID 或 after 回调不消费两次。
7. 完成时重新核对当前预检 hash、实体证据、送达 hash、本人确认及创建时快照；中途改字段/撤销证据则不完成。已创建 ID 不随重预检消失，不能把新草稿偷偷再创建。未知结果的人工核对/恢复接口未扩展，本次只输出阻塞状态。

**本地 WOULD_ALLOW 的含义**：满足当前插件的身份、草稿、API 参数及阶段条件；不是 GLPI 服务端迁移授权或生产执行成功。update 日志明确带 `server_transition=UNKNOWN`，结果/反馈带 `transition_runtime_verified=false`。它不等于 Enforce 准入，生产迁移仍 BLOCKED 待独立验证。

`get_ticket` 的 counts 是同一请求 ID 下 solutions 查询的数量，与本 Flow 的相关 add_solution 回执联合使用。它不是 solution 详情/单项 ID 读回，也不是事务快照；不能证明并发外部修改后仍存在同一条 solution。本任务不扩大 MCP 查询能力。状态/solution 的生产验收必须覆盖此限制以及 GLPI 正文回读格式。

去重只覆盖当前进程、当前有效 Flow 的已记录操作；256 个操作后不再登记新调用，不驱逐旧关联。TTL/进程重启后状态丢失。**Shadow 不实际阻断重复调用或其他写入；外部 REST、其他工具、跨 Flow/重启的全局幂等性不在其能力范围。** 这不是数据库事务或生产幂等保证。
